## 1. 关键设计问题与裁决（root 代答）

### Q1 三屏是什么？堆新页面还是同页分区？
裁决：**同一 `/c/[code]` 页内的三个状态分区**，不是新路由、不是任务大厅。理由：顾客从 NFC/扫码进入后只应有一处真相；三屏对应参与的三个阶段（了解→发布→领奖），阶段由参与状态推进而不是由顾客找入口。
1. **活动与优惠**：商家/门店、可得权益、需完成的动作、核验方式（店员见提交/店员核对作品/官方确认）、限额与保留期限、领取条件。先说明后操作；主动作按钮按实际写「选择内容并参与」，未达标不写「已领取」。
2. **内容与发布**：默认推荐一个 3553 已审核内容包（可播放/看文案/少量换选）；平台路线只显示 3535 对本活动已放行的（off/unknown 诚实显示不可用原因）；「在某平台继续」走 1670 PublishHandoff，媒体准备/失败恢复内联。
3. **领取或请店员确认**：读自身 3546 参与 + 1671 奖励状态；人工路径给参与码和「请店员确认」；官方路径给真实进度；实际发放后才显示券/码/门店/期限；已兑现标注已兑现、不再引导重复领券。

### Q2 参与生命周期怎么接线？
裁决：普通浏览只读公开活动面，**不建参与、不占奖励**（3546 纪律：浏览绝不建参与）。点「选择内容并参与」才 `POST /api/participations`（BFF→3546），展示实际 `benefit_reservation_state` 与 `expires_at`；未预留/无库存不引导发布（benefitCopy 纪律：只有 confirmed 说「已保留」）。选定内容 `PATCH /api/participations/{id}/content` 冻结前可换、attempt 交接后冻结。离开前出示参与码（3546 handoff qr_payload，受控、只显示一次的 discipline 遵循 3546 契约）。回到 H5/重开链接先 `POST /api/participations/lookup` 恢复，不重开。「我已完成」只发核验请求（1670 done 语义），不能自己让奖励通过。

### Q3 文案三态怎么保证？
裁决：核验三态文案唯一出口为常量表：`staff_observed_submission=店员见到提交`、`staff_verified_post=店员核对作品`、`official_publish_confirmed=官方确认发布`（与 1671 `evidenceText` 对齐）。本系统已确认发放（benefit status=issued）的奖励**不被外部 unknown 拖成「奖励未知」**：奖励卡状态判定优先级 issued/redeemed > 外部发布状态 unknown。

### Q4 安全边界？
裁决：公共数据仅公开字段白名单（快照/summary 服务端已白名单）；参与/券码限定本人受控会话（3546 visitor cookie，HttpOnly SameSite=Lax；券码不落 URL）；短码/query 不能换租户/提权（服务端 ResolveLink 定租户，前端不传 tenant 覆盖）；不采集密码/cookie；凭据 token 不写 localStorage/sessionStorage（沿 1670 红线）。

### Q5 异常矩阵（每项必须有真实恢复或联系门店动作）
未安装（平台 entry unsupported → 文案+导出+请店员确认）；版本不支持（entry 形状不合法→同上）；拒绝授权（发布主体声明+允许取消，取消有按钮）；下载失败（媒体 URL 形状不合法/缺失→提示+换选/请店员）；用户取消（cancel 恢复到可重开）；审核中（handoff status≠platform_confirmed → 保持进行中文案，不伪报）；页面丢失（恢复入口：lookup+参与码）；网络未知（fetch 失败→重试+参与码仍可出示）；奖励用尽（public summary available_qty=0 或 start 422 out_of_stock → 诚实告知+联系门店）；活动暂停/结束/不存在（沿五态文案，无参与表单）；库存最后一份（available_qty=1 提示「最后一份，先到先得」不承诺）；错码/过期码（404/gone 文案+联系门店）。

### Q6 视觉？
裁决：390/430 优先（单列、主动作拇指区、安全区 padding 复用 tk-public 卡片壳）+ 桌面可用（max-width 居中）；只复用现有 `tk-*` token（touch.css + painuo tokens），不改全局 CSS、不改根 layout；加载/错误/空状态完整（data-state 标注沿仓内惯例）。

### Q7 文件面与并行边界？
裁决：本票独占 `/c/[code]` 公共页布局与顾客状态组件：
- `web/src/app/c/[code]/public-campaign.tsx` 重构（保留 PublishHandoff 与 CustomerPublish 挂载、留资区块原语义）；
- 新目录 `web/src/components/customer/**`（三屏组件）+ `web/src/lib/customer-journey.ts`（纯函数状态机与文案唯一出口）；
- 不碰：/t 路由（1665 在飞）、商家页/店员台/规则配置、共享 layout/全局 CSS、既有留资流程组件。
1670 的 PublishHandoff 保持自足（它自己 fetch routes/start）；三屏把发布动作收敛到 PublishHandoff 的挂载位，不复制其逻辑。

### Q8 并行边界与 feature 门控？
裁决：FEATURE_CONTENT_PACKS / FEATURE_PARTICIPATION / FEATURE_REWARD_OPS / FEATURE_CHANNEL_ADMISSION 任一 off 时，对应区块**不冒充可用**：内容包 off → 显示「门店还没有准备好内容，请按现场说明参与」；participation off → 不显示「选择内容并参与」，只显示浏览面+留资基线；reward summary off → 奖励区显示领取条件说明但不显示库存数；admission off/unknown → 平台选择区诚实显示不可用原因（PublishHandoff 自身 404 隐藏逻辑保持）。测试替身只进测试文件。

## 3. 组件与状态机

```
PublicCampaign(重构)
├─ 屏1 ActivityIntro      —— 活动与优惠（含核验方式/限额/领取条件）
├─ 屏2 ContentPublish     —— 内容推荐/换选 + 平台放行路线（3535）+ PublishHandoff 挂载
│    └─ <PublishHandoff code={code}/>（1670，必须保留）
├─ 屏3 RewardStatus       —— 参与码/请店员确认 + 奖励真实状态
├─ 留资区块（原语义保留：独立可选，不做领奖门槛）
└─ 五态降级（原 degraded-state 保留）
```

`lib/customer-journey.ts` 纯函数（vitest 主战场）：
- `journeyStage(participation|null, reward)` → "browse" | "started" | "publishing" | "awaiting_review" | "reward_ready" | "redeemed"
- `rewardCardCopy(benefit, externalUnknown)` → 本系统已发放优先，unknown 不拖黑已发放
- `admissionLines(admission|off)` → 诚实不可用原因行
- `stockLine(slots)` → 限额/最后一份/用尽文案（available_qty 不伪报）
- `exceptionCopy(kind)` → 异常矩阵文案唯一出口
- 选择保持规则：`canSwitchDraft(participation, attempts)` → 未交接可换、已交接冻结
