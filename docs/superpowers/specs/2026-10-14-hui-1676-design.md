## 1. 领域增量放哪？→ 新叶子包 campaignenable，campaignrules 保持不动

- 问题：配置域（核验模式/奖励口径/去重语义/启用状态/告知快照）是塞进
  campaignrules 还是开新包？
- 裁决：开 `server/internal/campaignenable`（根裁决 1「必要时新叶子包」）。
  campaignrules 是带锁定测试的纯 4 字段评估器内核，它的形状就是 PR#8 的
  机器契约；把大配置塞进去会搅浑已收口的面。campaignenable 只做三件纯事：
  `ValidateSpec`（形状校验）、`Check`（启用前检查，固定顺序，机器原因码）、
  `BuildDisclosure`（告知快照）。零 SQL、零 HTTP。
- 消费面（只读，不复制状态）：
  - 3553 contentpack：内容事实由 HTTP 层组装——`GetContentPackVersion` +
    `ListAdoptions` + `contentpack.Distributable`（授权 grant_until 过期即拒、
    blocked 即拒）；配置只存 `content_version_id` 引用，不复制内容；
  - 3535 channeladmission：渠道事实 = `ListChannelAdmissions` 逐条过
    `channeladmission.Gate(RewardPlay=true)`；配置存
    (platform, entry_mode, scenario) 三元组，**不存在「只存平台字符串」的
    字段形状**；未登记路线 = unknown = 拒；
  - 1671 rewardops：权益引用 = `benefit_slot` + 版本对齐。启用前检查只**读**
    `ListRewardInventory`（批次 rule_version == 配置版本 且 available>0），
    零写入参与/奖励表。对 G3 的同步小契约 =
    `GET /campaigns/{id}/publish-config/snapshot` 返回 rewardops.Snapshot
    同形 JSON（campaign_id/version/allowed_evidence/slots）。

## 2. 配置流程与入口 → 五步一次配置，服务端持久草稿

- 裁决（根裁决 2）：组件 `web/src/components/work/campaign-config-panel.tsx`
  按「活动与门店 → 准备内容 → 发布方式 → 给什么优惠 → 顾客预览与启用」
  组织；草稿保存 = PUT（status 保持 draft）；刷新/重登恢复 = 挂载时 GET
  （服务端持久，不依赖 localStorage，重登换浏览器均可恢复）；不重复填
  门店资料（活动页只读展示 campaign/store）；无技术 ID 输入。
- 入口：活动详情页窄接线（ContentPackPanel 同款 2 行挂载 precedent），
  锚点 `#publish-config`；`/work/rewards` 选定活动后补一行窄链接指向该锚点
  （窄补丁选择，报告声明；不做主体改动，1671 页面零风险）。
- 反薅羊毛规则集（PR#8 的 4 字段）并入「给什么优惠」步：面板对
  既有 `PUT /campaigns/{id}/rules` 做第二次调用，两个保存各自独立事务、
  失败各自报字段；已锁定的 rules 端点零改动。

## 3. 三核验模式 → 配置时选定 + 写顾客文案，enabled 即快照

- 裁决（根裁决 3）：`verification_mode` 枚举 =
  `staff_observed_submission | staff_verified_post | official_publish_confirmed`
  （与 rewardops 三个 Evidence 类常量逐字对齐）。启用前检查强制
  customer_copy 非空（copy_missing 拒绝）——顾客文案在配置时写死，
  不在完成后临时加严。official 模式的不可伪装性由 rewardops.Adjudicate
  既有语义保证（OfficialRef 必须服务端事实）；本票不重实现。

## 4. 奖励配置口径 → 引用与预算，不建库存不发钱

- 裁决（根裁决 4）：benefit_kind ∈ store_coupon|imported_code|onsite_gift|
  onsite_discount；budget_mode ∈ total_quantity|cost_budget（二选一口径 +
  对应数值列）；daily_cap、store_ids、claim/redeem 窗、onsite_redemption、
  staff_verify_scope(store_staff|org_owner)、out_of_stock_action(stop_new|
  mark_sold_out)。现金/抽奖/POS 零字段。

## 5. 去重语义 → 判定基础显式三选一

- 裁决（根裁决 5）：dedup_basis ∈ verifiable_receipt（可验证消费凭据）|
  platform_authorized_subject（平台授权主体）| onsite_manual（现场人工）。
  按订单限领（per_order_limit）只在 verifiable_receipt 下可选；告知快照
  生成人话判定句（BuildDisclosure），cookie/IP 不在任何选项里。

## 6. 启用前检查（服务端强制）→ 固定顺序纯函数

- 裁决（根裁决 6）：`campaignenable.Check(spec, facts)` 固定顺序：
  copy/verification → content（未采用→blocked→授权过期）→ channel（closed
  →未准入/unknown→无可用渠道）→ benefit（引用缺失→版本不齐→无库存）
  → window（时间冲突/活动已结束）→ store（错店/错租户）。
  第一个阻塞原因胜出，原因码 + field 名随响应给 web 落到具体字段。
- 启用 = 钉住 `enabled_version` + 冻结告知快照 JSON + revision 'enable'。
- 预览 = 快照端点 + web「测试预览」横幅，零消耗（无任何写路径）。
- 顾客开始参与前的预留 = participation.BenefitReserver 既有端口
  （3546 已建，生产接线归 G2/G3）；本票保证：未启用/已暂停时快照端点
  如实返回 not_enabled，上游不得按「已承诺奖励」对待。
- 并发启用：条件 UPDATE（status IN draft,paused 才可置 enabled），
  0 行 = 他人已启用 → 读回现行返回 200（幂等，不双写 revision）。

## 7. 版本与在途 → 新版本即草稿化，老参与快照不动

- 裁决（根裁决 7）：每次 PUT = version+1 + 全量快照修订（0005 同语义）。
  **enabled 状态下保存 → 自动回 draft**（修改必须重新过启用检查，
  fail-safe：不出现「未检查的新版本继续在线」）；既有参与的
  rule_version/content_pack_version 由 participations 行自带（3546 已快照），
  永不回填；紧急暂停 = enabled→paused（revision 'pause'），参与/核验表
  零触碰 → 老参与核验/履约入口天然保留（staff 面读路径不经过本配置）。
- 普通浏览/留资链：本票全部新面都在 FEATURE_CAMPAIGN_RULES 与
  publish-config 端点之后，未配置的活动连行都没有 → 不存在强行升级。

## 8. 迁移与开关

- 0031 单文件（additive SQLite）：`campaign_publish_configs`（UNIQUE
  campaign_id 一行现行）+ `campaign_publish_config_revisions`（不可变全量
  快照，action ∈ create|update|enable|pause|resume）。JSON 列（store_ids/
  channels/disclosure）与 0028/0029 的 JSON TEXT 惯例一致。
- 开关：全部新端点挂既有 rulesGate（FEATURE_CAMPAIGN_RULES，默认 off）
  —— 本票就是规则编辑器，一个开关管整个编辑器；/work 面不新开开关。

## 9. 测试矩阵（全负例 + 恢复 + 隔离）

- campaignenable 纯函数：空内容/未采用/blocked/授权过期/渠道 closed/
  未准入/unknown/无库存/版本不齐/时间冲突/活动已结束/错店/copy 缺失
  → 各自机器原因码；正路径一次通过；固定顺序（多因并存时首个原因稳定）。
- store：版本递增、修订留痕五动作、跨租户 ErrNotFound、enabled 下保存
  自动草稿化、并发启用幂等、条件更新不双记修订。
- httpapi：off 基线 404（新端点不注册 + gate 双保险）、authz 仅
  org_owner、跨租户 404、enable 拒绝带原因码 + field、快照契约 JSON 形状
  = rewardops.Snapshot、draft 未启用时快照 not_enabled。
- 同版本证明：enable 后 `GetCampaignRulesByCampaign`（公共评估路径）与
  `GetCampaignRules`（管理读路径）读到同一 version 行（store 读取路径测试）。
- web vitest（node 环境源码级断言）：五步齐、三模式带文案、字段级错误
  映射、挂载即 GET 恢复草稿、预览带测试横幅、无技术 ID 输入、
  /work/rewards 窄链接、活动详情 2 行挂载。
