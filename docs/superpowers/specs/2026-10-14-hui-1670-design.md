# HUI-1670 顾客发布交接：真实渠道交接与恢复 —— 设计（brainstorming 落档）

日期：2026-10-14 ｜ 票：HUI-1670（碰一碰门店交付 B1｜FEAT-0171）｜ 分支：`hui-1670-publish-handoff`（基 origin/main @ 6b7ddca）

## 0. 基线声明（不重做项）

PR#15（44ce4bd）已交付预览/合规导出基线与四平台能力判定（`server/internal/custpublish`：预览/导出开，唤起/授权发布/确认发布关）。**该基线与包本体保留不动**。本票增量 = 「真实渠道交接与恢复」：把 PR#15 的纯前端能力判定升级为——
- 交接前强制过 3535 准入闸（服务端单点，前端隐藏按钮不算数）；
- attempt 级状态机落库（带证据来源字段）；
- 官方回执验签接口 + fixture 测试（真实确认保持 NOT_VERIFIED 残差）；
- 三种事实（人工见提交/人工核对作品/官方确认）分别落库，人工永不转官方。

## 1. 关键设计问题与裁决（root 代答 + 仓内事实推演）

### Q1 领域包放在哪？与四个已并权威服务的关系？
**裁决**：新建叶子包 `server/internal/publishhandoff`（发布交接/渠道适配/结果处理）。只 import 不改：
- `channeladmission.Gate`（3535）：交接前强制过闸——未知/未准入路线不得显示可执行；Record 由 httpapi 层经 `store.GetChannelAdmission` 解析后传入（保持叶子包零 SQL 依赖 store）。
- `participation`（3546）：attempt 创建/冻结（`CreateAttempt`→`BeginHandoff`）+ 交接凭据（短时单用途）复用；publishhandoff 不建第二套参与模型，不复制 benefit_slot。
- `contentpack`（3553）：已选版本快照（adopted + `Distributable` fail-closed）+ 受控媒体下载 URL（`NewHandoffClaim`/`MintHandoff`）；文件字节零过本服务。
- `publishreward`（1671）既有证据语义：本包只产出事实事件供其消费，不写奖励账。

### Q2 状态机长什么样？什么算证据？
**裁决**：`previewed → handoff_preparing → handoff_ready → editor_opened（仅可证实时）→ submitting → awaiting_review / platform_confirmed / canceled / failed / unknown`。
- `editor_opened` 只接受可验证证据源（verifier 接口判定）；窗口失焦、用户自报、点击事件一律不是证据（负例测试锁定）。
- 每次状态落库带 `evidence_source` 字段（`customer_action` / `staff_observation` / `official_receipt` / `system_timeout` / `system_recovery`…），无来源的状态迁移拒绝。
- `platform_confirmed` 只能由验签通过的官方回执到达；人工事实永不转换成官方。

### Q3 渠道适配怎么写？
**裁决**：按 `entry_mode` 写适配器接口（`h5` 深链构造 / `miniapp` 薄适配 / `manual` 导出指引），适配器只消费 Gate 裁决，不自带白名单：
- 抖音普通 H5 = `not_admitted`（3535 种子：官方规范明确排除营销内容）→ **拒绝交接**（`refused`），顾客页不展示该路线的发布 CTA，也不把手工导出当作该禁用玩法后门；
- 抖音小程序任务/小红书/B站/快手 = `unknown`（Gate 拒绝自动交接并给缺项原因）→ **诚实降级** `manual_only`：合规导出 + 手动指引（PR#15 基线语义），交接管道本身照常工作（恢复/取消/验签/幂等编码不因外部资格缺失而停）；
- `admitted`（当前种子无；测试以 fixture 注入）→ `automated`：适配器产出深链/小程序载荷，`editor_opened/submitting` 迁移可达。
- 官方回执 = 验签接口 + fixture 回执测试；真实平台确认保持 NOT_VERIFIED 残差。

### Q4 三种事实怎么落库？
**裁决**：`staff_saw_submit`（店员目测提交）、`staff_verified_work`（店员核对作品）、`official_confirmed`（官方确认）作为**独立证据事件**追加写入事件表（给 1671 消费），互不转换、不可改写。顾客「我已完成」只产生 `customer_done_requested`（核验请求事件），不触发奖励、不改变事实等级。

### Q5 媒体准备怎么做？失败会不会触发付费生成？
**裁决**：交接时从 contentpack 受控 URL 取已选版本媒体；服务端做结构性校验（content-type 白名单、SHA-256 格式、快照非空），实际可读性/格式/时长由发布器经受控 URL 拉取，组件侧显示进度与重试（URL 过期免费重铸，重试不新建 handoff）。换稿/换平台 = participation 新 attempt（3546 语义）+ 顾客重新确认，绝不静默换内容。**交接失败不触发任何付费生成——结构性保证：publishhandoff 包零生成调用、零付费端口、零外呼平台**（测试断言）。

### Q6 UI 组件放哪？公共页动多少？
**裁决**：自包含目录 `web/src/components/publish/**`（组件 + 状态文案映射 + 守卫纯函数）。`/c/[code]` 公共页只做**最小窄挂载补丁**（import + 挂载点，≤10 行）并在报告声明——公共三屏布局归 HUI-1896，本组件必须可被它独立集成。BFF 走既有 catch-all（`web/src/app/api/[...path]`），零改动；Go 侧路由集中在 `publish-handoff` 前缀。

### Q7 客户端安全边界？
**裁决**：不向浏览器下发内部 token/平台 secret/商家 cookie；回执验签只在服务端；交接凭据走 3546 短时单用途机制；媒体 URL 是 contentpack 短时效（≤1h）HMAC 受控 URL。回执回调端点不信任任何客户端声明的 success。

### Q8 幂等/重放/乱序/超时/重启怎么处理？
**裁决**：
- 同一次交接的重复请求按幂等键（participation+attempt+platform 派生）回原行，不新建；
- 官方回执按 `receipt_id` 唯一约束去重；重放回原事件；
- 乱序（confirmed 先于其他事件到达）：事件照录，状态只按合法迁移前进、绝不降级（晚到的 submitting 不回退 platform_confirmed）；
- 超时：`submitting` 超时 → `unknown`（`system_timeout`），先回查（Query 计数）不盲目重投；`unknown/timeout` 后拒绝重发（`query_required`）；
- 服务重启：全部状态在 SQLite，重启后同一 handoff 可继续回查，不重复投稿（重启负例测试）。

### Q9 迁移要不要？
**裁决**：两张新表（additive SQLite）：
- `0034_publish_handoffs`：一次交接一行（tenant/participation/attempt 冻结引用、platform+entry_mode+scenario、幂等键唯一、状态+证据来源、内容版本指纹、时间戳）；
- `0035_publish_handoff_events`：只追加证据事件（kind 白名单 CHECK、actor、payload JSON、receipt_id 唯一部分索引）。
参与尝试级状态仍归 3546 的 attempts 语义（handed_off/completed），本包不写参与表。

### Q10 HTTP 面与开关？
**裁决**：`FEATURE_PUBLISH_HANDOFF` 登记制开关默认 off（off = 路由不注册 + handler gate 统一 404，双保险同款）。顾客面（无会话，visitor cookie 语义与 3546 一致）：
- `GET /api/v1/public/links/{code}/publish-handoff/routes?platform=`：Gate 逐路线裁决 + 计划类型（automated/manual_only/refused）+ 缺项；
- `POST /api/v1/public/links/{code}/publish-handoff`：确认内容后开交接（过闸→attempt 冻结→handoff 行→受控媒体 URL→计划载荷）；
- `GET .../publish-handoff/{id}`：读自身交接状态+媒体 URL（过期重铸=弱网重试）；
- `POST .../publish-handoff/{id}/cancel`、`POST .../publish-handoff/{id}/done`（仅核验请求）、`POST .../publish-handoff/{id}/editor-opened`（无有效证明一律 422 evidence_required）；
- 回执回调 `POST /api/v1/public/publish-receipts/{handoffID}`：服务端验签+绑定核对+去重。
店员面（requireSession + authz 门店作用域，仅记录事实不建页面——3562 归店员页面）：`POST /api/v1/publish-handoffs/{id}/staff-events`（kind ∈ staff_saw_submit|staff_verified_work）。

### Q11 测试矩阵（票面红线）
- admitted fixture 路径全状态机贯通（`LoadAdmissionSeed` 注入 admitted 记录）；
- not_admitted / unknown 诚实降级 + 缺项原因 + 拒绝交接；
- 负例：重放回执、乱序回执、伪造回执（错签名/错 app/错租户/错 attempt/错内容版本）、跨租户读、窗口失焦冒充 editor_opened、自报冒充 confirmed、撤销素材（blocked 版本拒新分发）、用户取消、弱网重试（URL 重铸不新建行）、服务重启回查、超时先查不重投。
