## 1. 关键设计问题与裁决（root 代答逐条落地）

### Q1 页面与信息架构
新增 `/work/service`（核实过无等价路径；`/work/rewards` 是 1671 的管理台，不是店员台）。移动优先：390/430 主视口，桌面可用，沿 `tk-page` 既有响应式体系。首页只有三组高频动作：扫参与码/手输、待确认列表、已发放/已核销记录。店员默认自己门店：页面加载即取 `GET /api/v1/whoami` 的 `store_scope`，店经理所有读取/操作都按本店过滤（活动列表服务端已过滤，权益列表带 `store_id` 参数）；不渲染经营报表类内容。

### Q2 扫码与手输（防枚举短码）
- 扫参与码 = 顾客出示的核验凭据二维码（3546 签发的 `qr_payload = <base>/p/ptx_<22位>.<校验位>`）。页面从 URL 载荷提取 token，走 `POST /api/v1/participations/staff/peek`（新窄端点，见 Q7）打开参与卡。
- 相机不可用/权限拒绝 → 手输。裁决：**手输的就是这枚 `ptx_` 交接凭据**（顾客 H5 页可展示），不做新的"短码"命名空间。理由：a) 新短码必然可枚举，恰是票面红线禁止的；`ptx_` 凭据 128-bit 熵 + SHA-256 校验位（`participation.ValidTokenShape` 形状预检不打库）+ 短时 + 单用途 + 租户/门店作用域鉴权，天然满足"带校验位与限流、不可枚举获取他店顾客信息"；b) 零迁移（3546 表已有该凭据）。限流在服务端新窄端点上做（Q7），不在前端假装限流。
- 券码扫码 = 券码原文 → `GET /api/v1/reward-benefits/by-code?code=…`（新窄端点，见 Q7）打开核销卡。
- 全程不让店员手填数据库 ID（participation id / benefit id 一律由服务端从码定位）。

### Q3 参与卡内容与证据选项
卡面：活动（标题）、门店、参与状态（`participation.statusLabel` 五态）、规则版本、权益预留状态（`benefitCopy` 白名单：只有 confirmed 才说"已保留"）、有效窗口、发布尝试列表（平台/交接方式/冻结版本）、已有关联权益。不展示顾客手机号/visitor_id/内部工程文案。
证据选项**只来自活动冻结规则**：页面用参与卡上的 `benefit_slot + rule_version` 去批次列表（`GET .../reward-inventory`）里匹配那一条批次，其 `allowed_evidence` 就是全部选项：
- `staff_observed_submission`（现场见到提交）、`staff_verified_post`（现场核对作品）→ 可选；
- `official_publish_confirmed`（系统已有平台确认）→ **只读展示**（按钮不可选，文案说明等待服务端官方事实；伪造回执由 1671 `fabricated_official_receipt` 拒绝，UI 也不提供输入框）。规则只允许官方时，主动作禁用并说明原因。
自报（self-report）不出现在店员可选项里（那是 1671 `SelfReportVerdict` 的待核验队列，只读展示在"待确认"）。

### Q4 主动作
- 「确认符合条件并发奖」= `POST .../reward-confirm`，绑定 participation_id、benefit_slot、rule_version、evidence、store_id、event_id（幂等键，浏览器生成一次）、actor（服务端取会话）、note。**发放/核销事务全在 1671，前端零账本。**
- 「确认并现场兑现」仅当匹配批次 `kind=gift_discount`：同端点 `fulfill_now=true`（1671 同事务 issue+redeem，两条事实）。未确认实际交付 → 只按「确认并发放」（仅 issued）。
- 券类发放成功后：展示领取成功（诚实 outcome 文案）+ 掩码券码（点开才见全码）+ **独立核销入口**（核销按钮 → redeem 端点）。
- 「暂不符合」：选原因（顾客可补做后再请求）。**服务端零写入**——1671 无"拒绝"账本事实，本票不造第二本账；参与保持 awaiting_review/open，不发奖、不取消（取消是终态，会断顾客补做路径）。UI 明示"未发放任何奖励，顾客补做后可再次出示"。该语义作为本票裁决记录（Q9）。

### Q5 并发与重试
- 网络未知（fetch 抛错/5xx）：先**回查**（重拉权益列表按参与引用匹配 + confirm 端点同 event_id 重试由账本 replay 兜底），只有回查确认无事实才显示可恢复错误；**绝不提示顾客重领**。
- 两店员并发核销：1671 单事务原子（一行恰好一份），后到者读回 `already_redeemed` replay → UI 显示「已处理」+ `redeemed_by`/`redeemed_at`（处理人、时间来自权益行）。
- 重复扫码：peek 不消费凭据，同码再扫重开同一张卡（见 Q7）。

### Q6 服务与权限
- 页面+受控客户端适配；权限全走既有矩阵：查=read_record/read_list、审/发=update（店经理限本店）、核销=update（按权益行本店）、撤销=manage_publish_reward（org_owner 专属，店员不因此获得预算权/改规则权/导顾客权）。
- 确认绑定五要素（participation/rule_version/evidence/actor/时间）+ note；本票不新增任何照片/文件上传（默认不存顾客手机整屏照片，票面"确需上传"分支不做）。
- 二维码只定位+证明持有关系：内部 token 不进页面日志、不进 URL 查询串（POST body 内传输）；错误文案不含 token。
- 异常补偿/撤销入口仅 `role === org_owner` 渲染，强制原因，调 1671 reverse，保留原记录文案。
- 渠道准入绕过问题：店员确认走的是"参与已存在"的记录（顾客侧已过准入），店员台不提供任何"无参与发奖"路径——confirm 必须绑定真实 participation_id，1671 对 slot/版本/库存的校验兜底。

### Q7 新增窄端点（最小补丁，全部 httpapi 层）
1. `POST /api/v1/participations/staff/peek`（body `{token}`）：`PeekCredential` 定位 → 租户相符 + `requireScopedAction(read_record, 门店)` + `GetForStaff` 双 fail-closed → 返回参与卡载荷（参与视图 + `campaign_id` + `store_id` + attempts）。**不消费凭据**（重复扫码幂等；两店员可同时开卡）。响应是新组合类型，不改共享 `participationView` 白名单（顾客面不加字段，零泄漏增量）。
2. `GET /api/v1/reward-benefits/by-code?code=…`：按租户+券码定位权益 → 按权益行门店做 read_record 作用域鉴权（错店 404 掩蔽）→ 返回核销卡载荷。
3. 手输限流：进程内固定窗口计数器（键=成员 principal，token 类请求 peek/staff-redeem 共用），超窗 429 + 可恢复文案。仅内存、无 Redis（仓内无此基建，不引入）。
4. store 层为此新增一个**只读**查询 `GetRewardBenefitByCode`（additive，镜像 `GetRewardBenefit` 风格；不改 1671 任何既有路径）。

注册：`staff/peek` 放进 3546 既有 FEATURE_PARTICIPATION 注册段（与 staff-view/staff-redeem 同一可见性纪律：off=路由不注册）；`by-code` 在 reward 路由注册段（/work 管理面惯例，无 FEATURE 开关）。

### Q8 迁移
**零迁移。** 全部消费 0020-0025 既有表：参与/尝试/凭据（3546）+ 奖励库存/权益/操作流水（1671）。不需要 0036/0037。

### Q9 已裁决的"不做"
- 不做搭子（随身设备）入口；不做真实顾客参与码渠道交接（3531 联调，如实声明 NOT_VERIFIED）。
- 不碰 TodayDesk、活动详情、G2 公共页、导航槽位（HUI-2222 在飞，入口归它）、`/work` 其他页面、rewardops/participation 包本体。
- 不加 FEATURE 开关（/work 后台惯例）；不发真实券；不在前端写成功状态；不做照片上传。
