## 1. 领域包

新建叶子包 `server/internal/rewardops`，承载本票全部增量判定逻辑：

- 证据三态常量与判定（`staff_observed_submission` / `staff_verified_post` /
  `official_publish_confirmed`）。
- 库存批次（inventory batch）领域形状：kind（`store_coupon` / `imported_code` /
  `gift_discount`）、数量、面额、成本、有效期、适用门店、slot 与规则版本绑定。
- 外部券服务接口 `ExternalIssuer` + 幂等重询语义（只定义接口 + stub 测试）。

不动 `rewardrule` 评估器；不改 `publishreward` 既有导出；不引用任何 web/BFF。
包间依赖方向：`httpapi` → `store` → `rewardops`；`rewardops` 不依赖 store。

## 3. 证据三态与规则快照

- 三态语义：
  - `staff_observed_submission`：店员见到顾客提交（目测）。
  - `staff_verified_post`：店员现场核对作品。
  - `official_publish_confirmed`：官方确认发布。**仅**锚定服务端
    `customer_publish_attempts` 行（status=publish_confirmed 且
    receipt_source=official_query 且 platform_post_id 非空且 publisher=
    activity_customer）。客户端自报的回执字段永不采信 —— 伪造官方回执在
    HTTP 面即被拒绝。
- 活动允许哪类证据由**规则快照**决定。快照的落点：券批次行自带
  `benefit_slot + rule_version + allowed_evidence + rule_ref`。G3 不编辑活动规则
  （G1 拥有），只保存被告知版本的绑定与审计引用；确认请求声明
  participation + slot + rule_version，服务端按该版本批次快照判定。
- **仅官方模式**：批次 allowed_evidence 只含 official 时，店员/自报证据一律拒绝
  （`official_evidence_required`），继续等待真实官方事实；本部署渠道矩阵当前
  产不出 publish_confirmed 行，因此仅官方活动诚实地不可发放 —— 与 R3 基线一致。
- **人工与自报永不转换成 official**：benefit.evidence 记录实际采用的证据类型，
  不可改写（无任何 UPDATE evidence 路径）。
- **自报只进 pending_review**：顾客自报走 HUI-1670 既有 self-report 路径
  （attempt.self_reported=1）。有自报、无权益的参与出现在
  `GET /campaigns/{id}/reward-review-requests`（待核验清单）；店员确认后按快照
  发放，不无限待审。

## 4. 原子性与幂等

- 一份权益：`UNIQUE (tenant_id, participation_id, benefit_slot)`。
  所有发放路径先在同一事务内做库存占用计数检查
  （occupied = COUNT(benefits WHERE inventory_id=? AND status IN
  ('reserved','issued','redeemed'))；reversed/expired 不占额），再 INSERT/UPDATE。
  违反唯一约束 → 回读既有行，返回已处理结果（不 500、不二次发放）。
- 事件去重与权益唯一分开：同一 `dedup_key` 重放直接回放首次结果
  （replay=true）；不同事件（换 attempt、换渠道、人工+官方双证据、不同店员）
  打到同一 slot 时被权益唯一约束挡住，回读已处理结果。
- 两店员并发核销：UPDATE ... WHERE status='issued'，单条语句原子；
  恰一人成功，另一端回读 `already_redeemed`。

## 5. 发放与核销是两个事实

- 状态机：`reserved → issued → redeemed`；`reserved ⇄ expired`（到期释放，可重新
  预约同一条权益行 —— 恢复不新增第二份）；`reserved/issued/redeemed → reversed`
  （管理员更正，终态，原发放事实保留，不得再发 `slot_reversed`）。
- "确认并现场兑现"：一个确认事件，同一事务写两条流水（issue + redeem），
  终态 redeemed。只发未交付：仅 issue，终态 issued。
- 误审撤销：org_owner + 必填原因；append-only 更正记录（op=reverse），
  不删账、不 UPDATE 历史（状态列只前进，历史在 operations 里完整）。
- 官方回执晚到：只补证据维度（统计里 official 计数），不改既有权益的证据类型。

## 6. 预留

- 用户明确开始参与时原子预留（G2 受信调用 `/internal/v1/reward-reservations`，
  入参=受信参与引用 + slot + rule_version + ttl）；TTL 秒数必填且在操作前明示。
- 纯浏览不产生任何行；反复恢复调用 reserve 命中同一行刷新 TTL，不重复占额。
- 预留到期：`ExpireDueReservations(now)` 惰性清扫（列表/汇总/预留入口都先扫），
  reserved→expired + 系统流水；库存随之释放。
- 库存耗尽（available=0 或券码池空）拒绝新承诺（`out_of_stock`），不超发。
- 券码分配时机：首次 reserve 时一次性绑定（store_coupon 服务端生成随机码；
  imported_code 从池中原子弹出一码；gift_discount 无码）。过期预留的码不回池
  （保守：绝不二次给出同一码）。
- 外部券服务：只定义接口 + stub 测试（超时用同一幂等键查询、不换键重出票；
  结果未知 = `pending_unknown` 待确认，不显示发放成功）。不接真实三方，
  HTTP 面不因此新增生产路径。

## 9. 裁决未覆盖、本票自行决策的问题（附理由）

1. **规则快照落在券批次行**（而非独立快照表）：迁移裁决只给三张表；批次本就是
   "为某活动某 slot 某版本承诺的库存"，把 allowed_evidence/rule_ref 挂上去即可
   满足"保存被告知版本的引用/审计快照"，且规则版本中途变更=新批次行，
   在途参与按原 rule_version 批次判定，天然满足"在途按原快照"。
2. **官方证据锚定服务端 attempt 行**：客户端只给 fact_id（attempt id），服务端
   回读校验五要件；防伪造官方回执的最强可行锚点，语义对齐 publishreward.official()。
3. **店员动作用既有 ActionUpdate**：不改 authz.go（非本票独占文件）即可获得
   门店 scope 语义；撤销/批次用既有 ActionManagePublishReward。
4. **过期后可重新预约同一权益行**：UNIQUE 约束语义是"一 slot 一份权益"，
   过期=未交付；重新开始参与刷新同一行，永不产生第二份。已发放/已核销/已撤销
   则不可再预约/再发（`already_*` 回读或 `slot_terminal` 拒绝）。
5. **券码在首次预留时绑定**：预留即占实体码，避免"预留成功但发放时池空"的
   破碎态；过期不回码，宁少勿重。
6. **dedup_key 用部分唯一索引**：同事务第二条流水（fulfill 的 redeem）不能占用
   同一事件键；SQLite 部分索引精确表达"声明了键才去重"。
7. **顾客本人读券码的公共路径本轮不建**：顾客奖励卡归 HUI-1896（禁碰 /c/[code]）；
   公共 summary 只给计数。顾客取券需要参与身份语义（G2），列为残差。
8. **公开 summary 只暴露计数与 slot 余量**：面额/成本/码不进公共面；
   码只在管理面（authenticated）可见；operations.payload 不记码。

## 10. 测试矩阵（票面负例逐一对应）

最后一份库存竞争（两 confirm 一成一拒 out_of_stock）、预留到期释放后他人可约、
规则版本中途变更（在途按原版本、新参与按新版本）、双店员并发核销（一成功一
回读）、重复回调/同事件重放（replay 不二次）、越权（agent/禁用成员）、错店
（store_manager 出 scope）、撤权（Enabled=false）、伪造官方回执（自报回执字段、
不存在的 attempt、非 confirmed attempt）、仅官方模式人工/自报被拒、人工先发+
官方晚到不重复、服务重启后账目复算一致（operations 重算 = benefits 状态）、
券码池弹尽、撤销后再确认不得再发。
