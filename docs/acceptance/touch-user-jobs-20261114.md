## 独立审查发现及修复

### 门店、内容与版本

- 服务草稿和动作编辑原会渗入已发布页面：公开读面改为原发布快照，保留实时停用否决；发布指针与编辑冲突用原版本检查。
- 已blocked内容在采用新稿时会被覆盖为retired：采用、原指针和事件改为同事务；禁令保留，0137只修有原非空阻断原因的历史错态。
- 按平台采用关系冻结候选；声明“支持某平台”不能代替已采用事实。旧会话保原版本，不能刷新到新稿。
- 原第5版公开内容404源于用草稿创建时间检查发布候选：改用真实发布时刻，新发布保留纳秒精度。Terra未重存/重发原记录，原页面直接恢复正确v4内容。
- 未版本化旧首页首次存草稿时，缺少历史发布时刻导致原内容被清空：仅旧baseline保原捕获候选，不补入当前新采用内容。
- 无PUBLIC_BASE_URL时入口记录虽已保存，原界面却提供不可用复制/二维码；现保留原记录并明确配置尚未完成，不另建入口。

### 活动、库存与店员办理

- 保存活动草稿原会使线上版自动退回draft：正式读面统一解析原enabled_version对应修订；显式启用新稿才切换。
- 恢复操作只恢复原线上版，不发布暂停期间的新草稿。缺失或非法正式修订明确拒绝，不回退读取草稿。
- 只有publish-config暂停而campaign仍active时，原确认发券仍可成功：在原账本事务真正新增预留/发放前核正式生命周期，堵住先检查后暂停的竞态。
- 所有余量已被原参与预留时，恢复原版不再错误要求“新用户仍有余量”；批次自身停用仍拒绝。原预留可按原条件办理，新用户仍缺货，库存守恒。
- 店员原路径可拿活动A参与在活动B确认：补原参与活动、冻结版本绑定；未知结果按原event_id回查/重试，reserved不当issued。
- 正常参与的BenefitReserver原为空，商家页面却承诺先预留：`0a6fa46` 将正常 public start/action upgrade 接到原库存账本，真实写入 reserved 后才能显示已预留。规则版本与优惠正式版本分开，恢复原参与不能借用今天的新承诺。
- 预留未知或失效时，顾客先回查/重试原参与；服务端新交接与旧 handed_off attempt 同时核原预留，不让顾客在没有名额时继续投入。已发放/核销先认原有效事实，不因领取期结束变成待预留。
- 真正旧无承诺参与可能与后来首次正式版的数字版本号碰撞：`1150423` 按参与出生、配置创建和原始发布修订证明原合同；原参与继续原流程，不获得新库存。缺失或损坏正式修订不降级成 legacy。
- 首份草稿保存期间同样必须保护原合同：`5a42106` 只有在原参与早于配置创建、完整草稿修订链与当前状态一致且从未发布时，才继续原参与；草稿之前已经成立的有效 hold 仍确认同一权益，不以新草稿取消原承诺，也不能借草稿新分配库存。
- 最后一份预留自然到期后，原公开余量一直为零，导致新参与进不到真正释放预留的事务：`ae53f2f` 使只读余量与账本释放使用同一时间判据。浏览不写库，最终分配仍在原事务；截止前不回收，截止瞬间可释放，未知期限和 issued/redeemed 继续占用。Terra 独立复验并发只有一个真实新预留，旧参与抢回失败准确为 failed。
- 原活动“查看权益”误把活动 code 当成门店 code：`a358435` 复用原权益组件增加 `/c/[code]/benefits`，返回同一活动，不创建第二份券账。Terra 原活动实测入口、本人空态和返回；原库没有参与/券，不声称有正向券验收。
- 新版活动尚未启用时，旧“参考文案”仍可展开预览、确认、导出和发稿步骤，绕过原参与/预留：`0ef5509` 将已配置新版承诺的旧流程改为只读参考，服务端也在原旧端点拒绝新操作。未配置新版承诺的真正 legacy 活动保留原路径，历史记录不删除。
